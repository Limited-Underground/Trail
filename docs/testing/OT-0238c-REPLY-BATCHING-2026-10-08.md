# OT-0238c bounded reply batching, 2026-10-08

This computer-only increment reduces avoidable USB reply reads during the enrollment workflow. It does not extend any deadline or replace fresh checks with cached authority. Full OT-0238c enrollment acceptance remains open.

## Change and evidence

The response reader now uses the existing 2,048-byte line limit instead of a 64-byte read cap, limited by the freshly reported queued-byte count. Startup reads retain their separate 64-byte cap. Every actual SDK operation retains its original clock, identity and authority checks before and after the operation; parser, overflow, extra-reply, reentry, refusal and uncertain-outcome rules remain intact. The entire production delta is one line in `tools/enrollment_candidate_usb_client.py`.

A canonical CONTROL reply contains 108 value bytes and 233 framed wire bytes. When that reply is already queued, the old reader uses four reads and 28 guards; the corrected reader uses one read and 13 guards. Four NEXTCONTROL replies are requested after transcript confirmation and before COMMIT. Under that coalescing assumption the correction removes 12 artificial reads and 60 guarded checks. COMMIT and READY acknowledgements are already short and have no direct batching benefit. Fragmented arrivals still require separate freshly guarded reads.

Five focused tests passed, including the actual maintained controller/operator first flow with eight status transfers and closed handles. They compare queued replies with 1-, 7- and 64-byte SDK fragments, preserving commands and results. An in-memory old-cap control fails the discriminating read-count assertion without modifying the current source. Independent adversarial checks reject late extra bytes, read-return reentry and expiry after parsing. A separate largest-value check accepts the canonical 1,265-byte recovery reply in one bounded read with 13 guards.

Independent final review accepted 247 tests and 607 subtests across five affected suites: USB client 66, controller 45, operator 55, runner 71 and runtime 10. The original run exposed a stale privacy-test assumption that an already queued 98-byte EXPORT reply required more than one read. The corrected expectation requires one read and both fresh guard counters equal to 13, preserving the existing payload/privacy, reply-state and fixed-schema assertions. Production code did not change further; the original failed receipt/log is retained. Only the USB suite was rerun after that test correction, and the other four passing suites were reused at identical source/test pins. This is an explicitly composed accepted result, not a claim that the initial matrix passed.

The final matrix used fresh per-suite Python interpreters and process-local temporary storage, with synthetic SDK fixtures outside the sandbox to avoid the previously established hard-link restriction. Commands and exact pins are in [accepted-cohort-receipt.json](../../.private/ot0238c-query-efficiency-20261008/accepted-cohort-receipt.json); the [independent review](../../.private/ot0238c-query-efficiency-20261008/independent-review.json) also preserves the separate adversarial/bounds results.
