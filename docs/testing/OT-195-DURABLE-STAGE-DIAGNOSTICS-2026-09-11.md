# OT-195 durable stage diagnostic preparation

Status: host and matched-build preparation passed; physical execution remains gated.

## Scope and interpretation

The [OT-193 trial](OT-193-DIAGNOSTIC-TRIAL-2026-09-11.md) received no
bytes and did not establish whether firmware consumed the command. The
[actual-source lifecycle tests](OT-194-POLICY-LIFECYCLE-2026-09-11.md) found
controlled silent paths without establishing the physical cause.

This additive `heltec_v4_security_policy_diag` target preserves the frozen
OT-187 source, evaluation, console and strict command/receipt bytes. It adds an
independent NVS stage record before console installation. This deliberately
changes initialization order and storage timing; it is a diagnostic experiment,
not equivalent acceptance of the original lifecycle or product firmware.

The [record contract](../../firmware/components/security_diagnostics/stage_record_v1.json)
uses one eight-byte unsigned integer with a fixed schema/image marker, stage,
allowlisted error and CRC16. No command, challenge, key, device identity,
address, user time or arbitrary text is retained. The target refuses an existing
diagnostic namespace and attempts at most eight stage writes, each followed by
commit and exact readback. A storage error stops further diagnostic execution;
a recorded evaluation failure still follows the original refusal receipt path.

| Stored marker | What it establishes |
| --- | --- |
| admitted | The initial record exists; console installation may not have begun |
| install_result | Console installation returned; the fixed error distinguishes refusal |
| waiting | Input reception was the next operation; no command consumption is proved |
| input_result | Actual command/session admission returned, with a fixed refusal category |
| evaluation_enter | Evaluation lifecycle was next; completion is not proved |
| evaluation_return | The evaluation lifecycle decision and entropy-stop returned; evaluation may have been skipped |
| send_enter | Receipt submission was next; no byte delivery is proved |
| send_return | Submission returned; even `none` is not evaluation success or USB delivery |

A valid stored record does not prove the writer observed successful commit or
readback: an applied write may have returned failure or been interrupted.
The record describes only its own stage. Later stages overwrite earlier error
categories; the current record cannot reconstruct a prior evaluation result.
A CRC detects corruption, not malicious rewriting, authentication or rollback.
Only the unchanged strict receipt path can admit a policy result.
An absent record cannot distinguish failure before app entry from NVS
initialization or first-write failure. A last marker alone cannot distinguish
an SDK stall from reset or loss of power.

## Readback and restoration boundary

The decoder accepts exactly three plaintext NVS pages (12,288 bytes). It checks
page and entry CRCs, version/state/bitmap/lengths, namespace identity, unique
current records and supported variable-value closure. Unsupported, corrupt or
ambiguous layouts refuse. Erased prior stage records cannot supersede the unique
current record. Synthetic bytes generated by Espressif's official NVS generator
are included with source and output provenance; no actual device NVS is public.
The official fixture covers static integer/string layout. Blob closure and
erased-update cases use synthetic mutations, not actual SDK update/purge or
interrupted-flash traces.

Fresh-original admission rejects recognizable prior diagnostic namespaces and
unresolved records. Fully zeroed erased slots cannot be selected and may be
accepted. This proves absence of a selectable prior diagnostic record in those
bytes, not that the namespace never existed historically. Live original custody
and a single admitted candidate invocation remain separate requirements.

Both retained OT-193 original NVS captures also pass the new decoder's supported
layout and namespace-absence checks, after exact private package/file hashes
were verified. Those bytes are stale. This offline check does not establish
current device state, fresh live custody or permission to reuse either capture.

The new observation seam confirms serial closure and idle state, binds the exact
original NVS and role, then writes the durable restore-intent before one full-NVS
capture. Raw bytes are saved to an exclusive private file and checked before
fixed-field decoding. It delegates to the unchanged restoration function even
when capture, private saving or decoding fails. Restoration still independently
verifies the original application/full NVS and protected regions before reset.
Uncertain close, changed original or failed journal barrier blocks ROM access.

This is a tested restoration seam, not a complete executable successor. The
current bundle, operator and sealed runtime remain bound to OT-187; they cannot
execute this image or authorize its extra NVS operations. A fresh cross-layer
image/source/decoder/executor/restoration package, operator/ROM-child integration,
interruption and untouched-role release tests, isolated-runtime probes, and fresh
one-use physical scope are required before a trial. Old grants are consumed and
old live snapshots are stale. No hardware was accessed in this task.

   application span and full NVS restoration boundary are retained. USB

   product BLE and radio behavior are not exercised; US915 is prior bench context.

   version, dependency manager and compiler cache disabled, initially absent
   build directories. Compare BIN, ELF, map, configuration, bootloader, partition
   and initial OTA bytes, dependency closure and resource sections.
3. Boot/transport: preserve quarantine and strict command/receipt parsing. New
   pre-console NVS initialization can alter timing. No physical endpoint or SDK
   execution-time bound is established; no timeout was enlarged.
4. Ordering: one app owner, finite transitions, no per-byte/poll persistence.
   Actual console faults, command refusal, entropy cleanup and send failure are
   tested through composed source. No NimBLE callback/product flow changes.
5. Persistence: no erase recovery or raw new flash offset. Storage uncertainty
   stops advancement; full original NVS is the later restoration boundary. NVS
   initialization can itself modify pages before the first diagnostic record.
6. Composition: actual target, policy/crypto, console and storage tests plus the
   real decoder and unchanged restoration form software evidence. Device
   services are simulated. A complete future operator is still a separate gate.
7. Hardware: skipped in full. No flash, reset, ROM capture, phone/APK/bond action,
   radio, fresh live snapshot or physical grant. Each future node must be freshly
   identified and restored before the next is attempted.
