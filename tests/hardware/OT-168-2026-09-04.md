# OT-168 saved-owner reconnect successor physical acceptance

**Date:** 2026-09-04

**Result:** The isolated retained Heltec passed exact private identity,
application-only write, independent readback, sector-tail, visible-runtime,
one immediate saved-owner Android reconnect, app-process-death persistence, and
one warm physical-reset reconnect through Ready. The later approximately
4-minute-38-second ROM absence exhausted retries; automatic recovery did not
resume during the 78.664-second post-reset observation.

## Accepted host inputs

The saved-owner reconnect successor is host-validated. Exact target admission
requires `CONFIG_APP_REPRODUCIBLE_BUILD=y`, and two initially absent,
cache-disabled ESP-IDF v6.0.2 builds reproduce the application, ELF, map,
bootloader, partition table, generated configuration, and partition-source
tuple. The canonical 563,824-byte application has SHA-256
`91D4CEB48CCFBCD21AC97CE604C48FBCCA04D70408D2BF749C90CB053AD04824`.
The complete Windows Host matrix exits 0.

Build identity boundary: those two initially empty output-directory builds
used the same pre-publication working state and embedded project version
`110e543-dirty`. Reproducibility here means equality of those accepted builds,
not a promise that a later clean Git commit produces the same bytes. The
standard target derives its version from Git; a post-commit build can change
metadata and SHA-256 without changing runtime source. The exact installed
`91D4CEB4...` artifact and its physical results remain bound to that recorded
pre-publication state. A clean-publication rebuild is a separate artifact
acceptance gate; this publication performs no firmware rebuild or device write.

## Physical prewrite gate

The owner placed the intended retained test Heltec in ESP32-S3 ROM download
mode. Windows exposed exactly one anonymous generic USB serial endpoint. Using
esptool 5.3.1 at 115200 baud with the no-reset, no-stub ROM path, the preflight
read the complete 5,177,344-byte factory application range beginning at
`0x10000` before any write.

The complete read reached the exact required length, but its first 551,584
bytes did not match the previously recorded installed application SHA-256
`B34C95FEC6CA2D319A914292E1D04466A1276D52C5D52B144B42CBDF365684E6`.
The owner then confirmed with certainty that this was the same retained
test Heltec used for the phone work, excluding the other board as the
operational explanation. The temporary nonqualifying read was removed. A
hard-reset/run command was attempted before exit; after one requested normal
reset with BOOT released, the owner reported that the display returned. No
bootloader, partition table, OTA data, NVS, application, fuse, radio, or other
firmware region was written.

The Android app and service were not started or changed. App data, the saved
bond, and the retained owner secret were not intentionally modified. No
reconnect candidate, GATT discovery, authorization, Snapshot, or Ready result
was attempted or admitted.

## Comparison audit

Host-only audit independently reproduced the prefix-hash result with both the
reused .NET SHA-256 object and a fresh hasher. Esptool 5.3.1 changes flash
parameters only for an image written at the bootloader offset; it does not
modify application bytes at `0x10000`. Its four-byte padding is irrelevant
because 551,584 is already divisible by four, and sector handling cannot alter
the compared prefix. No 551,584-byte `B34C95FE...` artifact remains in the
workspace for independent reinspection.

The same-unit owner confirmation plus valid comparison proves that the factory
application bytes at read time were not the recorded `B34C95FE...` bytes. The
evidence does not distinguish an incorrect/stale earlier record from unexpected
installed-image drift because the nonmatching read and its actual hashes were
not retained.

## Owner-directed development identity and lineage successor

The isolated Heltec was re-entered into ROM mode after the host parser was
corrected to accept repeated identical esptool MAC observations while still
rejecting disagreement. `read-mac` enrolled the factory ESP32-S3 base MAC as
`OT-DEV-001` in the ignored development registry. After the complete application
read, an independent second `read-mac` exactly matched `OT-DEV-001`. The raw MAC
is retained only in `.private`; it is absent from this evidence and every
production artifact.

The exact 5,177,344-byte application-range capture at `0x10000` is retained in
ignored recovery storage with SHA-256
`BC2421E0D11AE84FD38C17F49A182E1215DAF5F9BD38BDFA62DD8178092D1EFF`.
Esptool `image-info` accepts its leading ESP32-S3 image, checksum, validation
hash, project `opentrail_heltec_v4_bench`, dirty source version `110e543`, and
ESP-IDF v6.0.2 metadata.

The capture's first 563,824 bytes exactly match the local pre-reproducible build
with SHA-256
`587A2D55D68EF8C19E9D48308EDD4B7AD6D4495F43A5618BD71335ED66BD0E81`.
The canonical two-build reproducible candidate remains
`91D4CEB48CCFBCD21AC97CE604C48FBCCA04D70408D2BF749C90CB053AD04824`.
The two 563,824-byte images differ at exactly 65 bytes: the 32-byte application
ELF digest field at `0xB0..0xCF` and the checksum plus 32-byte validation hash at
`0x89A4F..0x89A6F`. The old build configuration lacked
`CONFIG_APP_REPRODUCIBLE_BUILD`; the canonical pair enables it. No other byte
differs.

This classifies the earlier `B34C95FE...` expectation as stale: the board
contains the exact later pre-reproducible successor build, not unexplained flash
drift. Exact device identity, installed-image lineage, and a recovery source are
now reconciled prospectively for `OT-DEV-001`.

## Authorized canonical write and immediate saved-owner reconnect

After a host power interruption, no write had begun. The owner reaffirmed
`proceed`, and the gate repeated the exact endpoint, recovery-artifact, phone,
canonical-artifact, and private `OT-DEV-001` identity checks before writing.
The dedicated Note20 was Android 13 model `SM-N986U`; its installed debug APK
matched the local artifact at SHA-256
`3DDB3F596A640DD087112864EBB75A326D7E8E6C0C0FEA19BA80974E9A414EEB`.
The app and foreground service were force-stopped without clearing app data or
the saved Android bond.

The current prewrite application prefix matched the retained
`587A2D55D68EF8C19E9D48308EDD4B7AD6D4495F43A5618BD71335ED66BD0E81`
image. The 563,824-byte canonical application was then written at `0x10000`.
An independent exact-length readback matched SHA-256
`91D4CEB48CCFBCD21AC97CE604C48FBCCA04D70408D2BF749C90CB053AD04824`.
The required erase covered `0x10000..0x99FFF`; all 1,424 bytes between the
application end and that sector boundary were `0xFF` before and after, so the
sector-tail state was unchanged. Esptool reported no internal write retry.
The private factory identity matched `OT-DEV-001` before the write and after
readback. No bootloader, partition table, OTA data, NVS, eFuse, or other region
was written.

A final read-only ROM identity command with hard-reset exit completed
successfully. After one normal physical reset with BOOT released, the owner
confirmed the display returned. The existing Note20 app was then opened, the
Bluetooth device mode was selected, and the connected service was started once
at 2026-09-04 18:53:13 EDT. The UI first reported `Checking for authorized

state remains authoritative.`, and the mandatory Snapshot values `radio

Android reported service-discovery status 0 at 18:53:43.894 EDT. The same
authenticated Ready screen and Snapshot remained visible at 18:54:50 EDT;
the retained screenshot was visually checked, and the owner also confirmed

At that stage, this accepted exactly one immediate saved-owner reconnect through

## Extended absence: retry exhaustion reproduced

The owner requested a 4-5-minute ROM-mode absence, then waived the remainder of
the planned hold after retry exhaustion was established. This used the same Heltec V4.2
`HTIT-WB32LAF` OT-DEV-001 and Note20 Ultra SM-N986U / Android 13, unchanged
canonical `91D4CEB4...` firmware and `3DDB3F59...` APK. USB remained connected;
this was neither a true cold-power nor physical range test. LoRa was not used
and no frequency/radio configuration changed.

Before entry, the phone showed authenticated Ready and mandatory Snapshot.
The sole freshly enumerated native USB endpoint was entered using esptool
5.3.1 `--chip esp32s3 --port <fresh-port> --baud 115200 --before usb-reset
--after no-reset --no-stub read-mac`. Its factory identity matched the private
OT-DEV-001 registry at 19:33:56.487 EDT, and the serial tool exited. No serial
action occurred during the hold, and the Android app received no taps,
restart, manual reconnect, or mode/service changes throughout the experiment.

The old-link callback arrived at 19:34:01.026. The app made exactly three
reconnect calls, at 19:34:02.048, 19:34:09.086, and 19:34:18.126. Each failed
with Android GATT status 133 about five seconds later; the last failure was
19:34:23.151 and final lease close/unregister finished at 19:34:23.158.
The terminal UI, retained at 19:35:06.869, showed `Bluetooth connection
unavailable`, `The bounded reconnect attempts were exhausted`, support code
`BLE-DISCONNECTED-BEFORE-PROFILE`, and `Scan again`.

After fresh sole-endpoint enumeration, esptool `--before no-reset --after
hard-reset --no-stub read-mac` matched OT-DEV-001 again and completed normal
hard reset at 19:38:34.167. The verified-ROM-entry-to-reset-command-completion
interval was 277.680 seconds (approximately 4 minutes 38 seconds), not an
instrumented application boot interval. The owner confirmed display return;
no physical reset fallback was needed. A host timestamp subtraction error
occurred only after successful reset/identity verification; it was corrected
read-only, without repeating the hardware operation.

At 19:39:52.831, 78.664 seconds after reset-command completion, the same app
process remained on the exhausted-retries screen. Captured Bluetooth logs
contained only the three outage reconnect calls and none after return.
Android automatic rediscovery after retry exhaustion did not occur during
this 78.664-second post-return observation; no post-return GATT attempt was
made. Automatic recovery for this tested absence therefore **failed**.
The Heltec was restored with its display on; the phone was deliberately left
in terminal failure so the observation was not obscured by a manual retry.

No flash, erase, stub upload, PIN, rebond, app-data clear, reinstall, factory
reset, second-device/phone, or radio operation occurred. Logs, UI XML, and
`result.json` are retained under the ignored local evidence directory
`.private/hardware-recovery/OT-DEV-001/long-absence-20260904-1934/`.
The existing immediate/warm-reset passes remain valid; this characterizes the
previously open long-absence gap. Next is bounded periodic saved-owner
rediscovery after fast retries, with fresh authorization/Snapshot before Ready.
OT-168 remains partial; Android 60%; V1 exact 43.75% / displayed 44%.
