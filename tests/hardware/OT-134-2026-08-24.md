# OT-134 Windows raw-evidence checkout determinism

## Failure history

- Last green before the streak: Host validation run 210, OT-092, commit `0afac6b1cf3d142aca2f2cae98264f80ee801989`.
- First red: run 211, OT-093, commit `e144e683d5a07fb4e305f95895f4f07cffb2d869`. It failed the older OTCBL0 raw firmware-input manifest assertion, not OTCAI; OTCAI did not exist yet.
- First exact OTCAI `contract digest mismatch`: run 217, OT-098, commit `180b340f9afc8a58c17fc39e6545c2cad2cde43a`, where the artifact, validator, test, and Test-Host registration first appeared together.
- The same OTCAI signature continued through run 261.

## Exact reproduction

Artifact: `tests/benchmarks/crypto/OT-098-OT005-EXTERNAL-CANDIDATE-ACQUISITION-V0.json`

- Exists: yes
- Canonical length: 5,454 bytes
- `MAX_BYTES`: 131,072
- Canonical and expected SHA-256: `b7be03e305c6253e10f69f624132a736cce5aea3f559760cde4f948ae79abad6`
- Canonical encoding: no BOM, 40 LF line endings, final newline present
- Unpinned Windows checkout: 5,494 bytes, 40 CRLF line endings, SHA-256 `058d793018496c0a512059fa6b1d838f2c08d54bd2440c802ab8f8ff64e3e909`

The file was neither empty nor oversized. Git history and blob comparison found no content, serialization order, timestamp, path, metadata, BOM, or final-newline change between OT-098 and current. The accepted artifact and digest are authoritative and remain unchanged. The cause was `core.autocrlf=true` acting without a path-specific attribute.

## Correction and validation

.gitattributes now defines deterministic checkout policy for every known raw-bound contract input: LF for canonical text, CRLF for the few authoritative CRLF files, and exact byte preservation for nine intentionally mixed-EOL files. Those nine Git blobs were restored to their already-pinned byte identities; no accepted content or hash was changed.

The new OTRBC0 audit checks 69 inputs without failing at the first mismatch and prints existence, actual and expected length and SHA-256, EOL form, BOM, final newline, and effective attributes. It is registered near the start of tools/Test-Host.ps1. Focused OTCAI tests pass 4/4, OT-099 passes 5/5, and OT-100 passes 6/6.

The first correction commit e4f36bc8862798847e56335f10b49be16a9b5c2b produced Host validation run 262. That run proved OTCAI 4/4 and OT-099 5/5 green, then exposed the same checkout conversion in the later OT-100 artifact. Commit a40bc2a3005a86544d313fcc2512a2956c1e0376 and run 263 then proved all 69 byte policies and every crypto gate through OT-114 before exposing a separate hidden CI issue: the default depth-one Actions checkout did not contain the frozen OT-092 and OT-093 commits required by the OT-093 historical successor gate. Host validation now fetches complete history, and an early two-group regression requires both the workflow policy and the exact historical commit objects.

No connected Heltec device or phone was used. No accepted artifact byte, pinned digest, validation limit, firmware, product capability, score, or public status changed. A public website update is therefore not required.
