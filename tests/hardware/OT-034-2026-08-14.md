# OT-034 build-only Heltec V4 ESP32-S3 target evidence

Date: 2026-08-14

Result: build passed; **NOT-FLASHED**

## Scope

This acceptance compiled the repository's bounded
`firmware/targets/heltec_v4_bench` candidate with ESP-IDF v6.0.2 for
`esp32s3`. It did not discover, open, select, erase, write, reset, reboot, or
otherwise access a physical device.

The application contains one fixed startup line and one recurring heartbeat.
Its only application-owned dynamic value is boot-local elapsed milliseconds;
it reads no device-specific identifier. ESP-IDF boot/runtime console output
remains unreviewed until a separately authorized physical-runtime test.

- `tools/Build-HeltecV4BenchTarget.ps1` exited 0.
- ESP-IDF reported `ESP-IDF v6.0.2` and target `esp32s3`.
- Generated configuration selected `USB_SERIAL_JTAG` as the primary console and
  contained no competing console selection.
- ESP-IDF size analysis passed: 141,965 application bytes, with 86% of the
  application partition free.
- A second incremental invocation exited 0 in 8.05 seconds, retained the exact
  generated target/console configuration, and reproduced every artifact hash.
- The ignored build evidence was explicitly marked `NOT-FLASHED` and

## Image-header boundary

The build produced a valid ESP32-S3 image, but its current header is the generic
2 MB flash, DIO, 80 MHz configuration with application version 1 and no embedded
timestamp. It is not an authoritative profile for the observed 16 MB flash and
2 MB PSRAM Heltec candidate. Exact flash-size/mode, PSRAM, partition, board
revision, and recovery settings must be frozen and rebuilt before any write.

## Evidence boundary and next gate

This is native compile, configuration, size, artifact, and incremental-build
evidence only. It is not exact-received-board, physical boot, console-output,
recovery, radio, BLE, GNSS, storage, power, display, security, or
supported-hardware evidence.

Before a physical write, the owner must intentionally authorize replacement of
the current MeshCore image and choose one sacrificial-first unit. That same unit
must first enter manual ESP32-S3 ROM download mode and have its recovery path
recorded. Runtime output must then be reviewed before the second unit or any
radio binding proceeds.
