# OT-009 Three-Node Repeater Bench Proof

Date: 2026-08-08

Status: partial; bounded close-range MeshCore forwarding and a software-forced
repeater path are proven, while a direct-radio OpenTrail binding and field
evidence remain

## Purpose

Identify the available Seeed solar node over USB, verify its repeater
configuration and health, establish bidirectional control traffic with both
Heltec companions, and prove that the repeater receives and retransmits flood
packets during a private two-companion sample. Then force direct-message routing
through the repeater and use a repeat-off negative control to prove that the
destination cannot accept the physically audible original packet before the
configured route hop is consumed.

This is not a forced-path test. All three radios were on the same close-range
bench, so the companion nodes could also hear each other directly.

## Setup

- `OT-DEV-001`: Heltec V4 OLED USB Companion, `COM6` during this run
- `OT-DEV-002`: Heltec V4 OLED USB Companion, `COM11` during this run
- `OT-DEV-003`: runtime board `Seeed SenseCap Solar`, MeshCore Repeater
  `v1.16.0-07a3ca9`, `COM17` during this run
- All three: 910.525 MHz, 62.5 kHz bandwidth, SF7, CR5
- Heltecs: 10 dBm; SenseCAP repeater: 22 dBm with repeat enabled
- Antennas were attached; all devices were USB-connected on the same bench

## USB and health evidence

The SenseCAP enumerated as USB `VID 2886`, `PID 0059`. Its repeater console
reported 4.155 V, zero core errors, an empty queue, -110 dBm noise floor, and
zero receive errors. Its freshly flashed clock was stale and was synchronized
to current UTC over USB.

Both Heltec contact lists already contained the SenseCAP repeater advert.
`req_clock` then returned the current repeater timestamp independently through
`COM6` and `COM11`, proving companion-to-repeater requests and repeater replies
at the application level.

MeshCLI 1.5.7 `req_status` did not return a parsed status within 15 seconds,
although radio counters changed during the request. This is recorded as a
command/firmware compatibility question rather than radio failure because
remote clock requests succeeded from both companions.

## Private forwarding sample

The existing private-sample harness created a temporary channel in slot 1 on
both companions, sent one unique numbered message in each direction, and erased
and verified the slot during cleanup. The channel secret and message markers
were generated in memory and were not logged.

| Direction | Delivered | Lost | Duplicates | Latency | SNR |
| --- | ---: | ---: | ---: | ---: | ---: |
| `COM6` to `COM11` | 1/1 | 0 | 0 | 240.8 ms | 11.5 dB |
| `COM11` to `COM6` | 1/1 | 0 | 0 | 276.9 ms | 12.0 dB |

The SenseCAP repeater counters changed from 4 flood RX / 2 flood TX to 6 flood
RX / 4 flood TX: exactly +2 received and +2 retransmitted flood packets. Its
receive-error count remained zero. Both companion queues ended empty with zero
new core or receive errors, and temporary-channel cleanup succeeded on both.

## Software-forced route and negative control

Physical isolation was unavailable, so the test used MeshCore's explicit
contact route instead. The companions exchanged temporary zero-hop adverts,
then each peer contact was assigned a one-hop direct path containing the
SenseCAP repeater's 1-byte path identifier.

With repeating enabled:

- `COM6` to `COM11` delivered the private marker and its acknowledgement with a
  1,121 ms round trip. The repeater recorded exactly +2 direct RX and +2 direct
  TX, accounting for the message and returning acknowledgement.
- After the negative control, `COM11` to `COM6` delivered the reverse private
  marker and acknowledgement with an 880 ms round trip. The repeater again
  recorded exactly +2 direct RX and +2 direct TX.

For the negative control, repeating was disabled over the SenseCAP USB console
and verified off. `COM6` sent another direct message with the same stored
one-hop route. The repeater recorded +1 direct RX but +0 direct TX, the sender
timed out waiting for its acknowledgement, and `COM11` had no application
message to retrieve. This proves that the directly audible original packet was
not accepted at the destination while its repeater path element remained.

Repeating was immediately restored and verified on before the reverse positive
test. Both temporary peer paths were reset, both peer contacts introduced only
for this experiment were removed, and each companion's contact list returned to
its original repeater-only state. The final SenseCAP snapshot reported 4.166 V,
zero core/receive errors, an empty queue, and repeat enabled.

## Evidence boundary and next gate

This run proves that the third physical radio is usable as a MeshCore repeater,
that it retransmitted both private flood samples, and that explicit direct
messages required it to consume their configured route hop. The repeat-off
negative control supplies the forced-path evidence without making a physical
range claim.

The run does not exercise the experimental OpenTrail packet-v0 codec or host
forwarding-controller policy on this hardware. The remaining OT-009 hardware
gates are a direct SX1262/OpenTrail binding and later field measurements of
range, obstruction, mobility, and congestion.
