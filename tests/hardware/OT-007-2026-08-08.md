# OT-007 Two-Node Versioned Message Proof

Date: 2026-08-08

Status: complete for the bounded experimental packet-v0 proof

## Purpose

Prove that a versioned OpenTrail frame can cross the transport abstraction in
deterministic host tests and pass between both available physical radios while
being encoded and decoded by the same C++ codec.

This is not a production protocol, direct SX1262 board binding, field-range
result, or security validation.

## Software evidence

- `RadioTransport` accepts opaque frames, reports MTU/state/errors/queues/link
  metadata, and has no identity, encryption, retry, acknowledgement, TTL, or
  forwarding policy.
- `FakeRadioTransport` passed eight scenarios covering binary frames, latency,
  queue saturation, unavailable/fault states, undersized receive buffers,
  injected errors, deterministic loss, and pausing queued traffic while offline.
- Packet v0 passed six codec scenario groups covering budget, the standard
  CRC-16/CCITT-FALSE check vector, binary round
  trip, encode validation, incompatible/malformed frames, identity validation,
  and CRC corruption.
- Two integration scenarios passed: a v0 packet crossed the C++ transport
  interface and decoded intact, while a deliberately corrupted packet crossed
  the transport but was rejected by the codec.
- All C++ sources compiled as C++17 with GCC 16.1.0 using `-Wall -Wextra
  -Wpedantic -Werror`.

## Physical setup

- `OT-DEV-001`: Heltec V4 OLED, MeshCore USB Companion `v1.16.0-07a3ca9`,
  `COM6` during this run
- `OT-DEV-002`: Heltec V4 OLED, same firmware, `COM11` during this run
- Both: 910.525 MHz, BW 62.5 kHz, SF7, CR5, 10 dBm, repeat disabled
- Both antennas remained attached and both units were USB powered on the same
  close-range bench
- Preflight: zero core/receive errors and empty queues on both devices

## Experimental adapter path

The direct Heltec/SX1262 OpenTrail binding does not exist yet. For this proof,
`Test-OpenTrailTwoNodeV0.py` used this bounded adapter path:

```text
C++ packet-v0 encoder
  -> opaque 35-byte frame
  -> URL-safe base64 MeshCore channel-text adapter (51 characters)
  -> temporary private MeshCore channel
  -> LoRa
  -> matching receiver adapter
  -> original 35-byte frame
  -> C++ packet-v0 decoder and field/CRC verification
```

The temporary channel secret, experimental network ID, node IDs, message IDs,
and payload markers existed only for the run. No identity, coordinate, public
key, PIN, or long-lived secret was printed or stored.

## Results

| Direction | Delivered | Lost | Duplicates | Latency min/median/max | SNR min/median/max |
| --- | ---: | ---: | ---: | ---: | ---: |
| `COM6` to `COM11` | 3/3 | 0 | 0 | 365.6 / 367.7 / 367.8 ms | 11.5 / 11.75 / 11.75 dB |
| `COM11` to `COM6` | 3/3 | 0 | 0 | 366.9 / 409.1 / 412.4 ms | 11.75 / 11.75 / 11.75 dB |

Every decoded frame had the expected version (`0`), experimental probe type
(`F0`), ephemeral source/network/message identifiers, payload, and valid
CRC-16/CCITT-FALSE.

Each device recorded exactly +3 packets sent, +3 received, +3 flood TX, and +3
flood RX. Both recorded zero new core errors, zero receive errors, and an empty
final queue. Coarse firmware counters increased by one second for TX airtime and
one second for RX airtime on each device. Firmware RSSI remained invalid at
zero; SNR ended at 11.75 dB on both.

## Cleanup

The temporary private channel was erased on both companions in the script's
`finally` block. A readback verified the slot name was empty on both devices.
No firmware, radio configuration, device identity, or persistent non-channel
setting was changed.

## Post-five-hour-soak regression

After the separate 300-minute three-node soak completed and cleaned up, the
same recoverable packet-v0 adapter ran another three probes in each direction:

| Direction | Delivered | Lost | Duplicates | Latency min/median/max | SNR min/median/max |
| --- | ---: | ---: | ---: | ---: | ---: |
| `COM6` to `COM11` | 3/3 | 0 | 0 | 417.2 / 656.2 / 1099.7 ms | 11.25 / 11.25 / 12.0 dB |
| `COM11` to `COM6` | 3/3 | 0 | 0 | 367.3 / 369.7 / 412.1 ms | 11.25 / 11.5 / 11.5 dB |

All six 35-byte frames again decoded with valid packet-v0 fields and CRC.
Each endpoint recorded +3 sent, +6 received, +3 flood TX, +6 flood RX, zero
core/receive errors, and an empty final queue. The SenseCAP remained repeat-on,
zero-error, and empty-queue; its aggregate counters increased by +5 flood RX
and +5 flood TX during the bounded run, which is observed relay activity rather
than proof every application delivery depended on the repeater. Both endpoint
channel cleanups were true, the exact-name slots verified empty, and no packet
lease journal remained. Post-run batteries were 4.209 V and 4.052 V; the
SenseCAP reported 4.187 V.

## Limitations and next gate

- Six close-range frames do not establish range, mobility, obstruction,
  congestion, reboot, or multi-node performance.
- The base64 text adapter adds overhead and is not the future direct-radio wire
  path. Its 96-byte experimental frame cap is deliberately conservative and is
  not a measured MeshCore or LoRa maximum.
- Packet v0 itself has accidental-corruption detection only. Separately tested
  host policies now cover identity lifecycle, priority, delivery/retry,
  acknowledgement, duplicate suppression, forwarding, and external alert ACKs,
  but these are not yet an authenticated physical packet-v0 composition.
- Exact regional constraints and physical antenna/RF details remain separate
  gates.

The next physical protocol gate is a direct SX1262/OpenTrail binding plus
authenticated identity/routing/priority composition; field range, mobility,
contention, and regulatory evidence remain separate.
