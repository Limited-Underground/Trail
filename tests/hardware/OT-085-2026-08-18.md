## Accepted evidence

- One fixed 16-byte `OTB0/v0` public link-information value encodes only
  protocol/transport bounds with zero capability bits. It contains no device,
  phone, owner, group, radio, location, key, path, or operation identity.
- A fourth characteristic under the existing service uses UUID suffix `0x04`
  and `READ` only. The existing protected Protocol Info, Command, and Stream
  permissions remain encrypted/authenticated/authorized and are not weakened.
- The serialized BLE owner accepts one link for 15,000 ms, requests exact-link
  termination, allows 2,000 ms for the matching disconnect callback, and then
  returns through the existing bounded re-advertising path. Missing or failed
  termination acknowledgement contains the runtime.
- Authorization claims and normal commands remain closed in every state. The
  display mapping uses only `BLE ADVERTISING` and `BLE CONNECTED`; connected
  means transport link only, never trusted, paired, authorized, or Ready.
- Strict focused C++17 tests pass: five fixed public-link scenario groups and
  fifteen serialized BLE-owner groups. The complete 148-executable native host
  gate passes. The Heltec static admission suite passes all eleven groups.

  image is 471,456 bytes with SHA-256

## Boundary

OT-085 proves source, host behavior, static admission, target compilation, and
reproducibility only. It does not prove that the new image was flashed, that a
phone connected, that the public characteristic was read over the air, that
the OLED changed on hardware, or that the link is stable in use.

Rollback-protected companion authorization remains deferred under Decision
0028. BLE writes, ownership, provisioning, persistence, radio/GNSS functions,
messaging, protected recovery, OTA/DFU, and Ready remain unavailable. A later
physical flash and live phone/display acceptance requires separate explicit
owner authorization.

V1 Companion remains exactly 39.75% and displays as 40%; no milestone
completion changed.
