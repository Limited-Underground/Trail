# OT-017D Host-Mediated Physical Critical-Alert ACK Round Trip

Date: 2026-08-09

Status: passed for the bounded close-bench adapter described here. This is not
an authenticated physical peer binding, direct OpenTrail radio firmware, a
field route result, or production delivery evidence.

## Purpose

Carry one exact 64-byte OpenGauge `OGA0` critical-alert frame over the current
MeshCore USB-companion text adapter, process it through the real OpenTrail C++
ingress and final-decision ACK responder on the host, return the correlated
64-byte `OGK0` frame over radio, and decode/correlate it at the originating
host. Repeat with the two Heltec roles reversed while observing the SenseCAP
repeater read-only.

## Bench and safeguards

- endpoints: two runtime-identified Heltec V4 OLED boards running MeshCore USB
  Companion `v1.16.0-07a3ca9`;
- observer/relay: runtime-identified Seeed SenseCAP Solar running the matching
  MeshCore Repeater build with repeat enabled;
- radio profile: USA/Canada, 910.525 MHz, BW 62.5 kHz, SF7, CR5;
- input: public normative `engine_over_temperature_asserted` `OGA0` fixture;
- adapter: URL-safe base64 in temporary private MeshCore channel text;
- channel: fresh 16-byte secret held only in memory;
- recovery: non-secret exact-name lease journal, removed only after both
  endpoints verified the temporary slot empty;
- repeater access: read-only `get repeat`, `stats-core`, and `stats-packets`.

`CriticalAlertBridgeCli.cpp` decoded and accepted the alert only with an
explicit host-supplied authenticated/authorized producer context. It then ran
`CriticalAlertIngress` and `CriticalAlertAckResponder`; the returned ACK was
decoded by the same production OpenTrail codec and checked against every
correlation field. Consumer/session values were ephemeral and were not written
to this evidence.

## Results

Two role-reversed cycles passed:

| Measure | Cycle 1 | Cycle 2 |
| --- | ---: | ---: |
| Alert delivery | 1/1 | 1/1 |
| ACK delivery | 1/1 | 1/1 |
| Alert latency | 500.6 ms | 495.3 ms |
| ACK latency | 498.0 ms | 499.4 ms |
| Host-observed round trip | 1014.0 ms | 1009.6 ms |
| Alert SNR | 11.75 dB | 11.25 dB |
| ACK SNR | 12.25 dB | 11.75 dB |
| Alert/ACK frame bytes | 64 / 64 | 64 / 64 |
| Adapter text characters | 91 / 91 | 91 / 91 |
| Duplicate alert / ACK | 0 / 0 | 0 / 0 |
| SenseCAP flood RX / TX delta | +2 / +2 | +2 / +2 |

Every decoded ACK check passed in both cycles: accepted disposition with reason
none, producer, consumer, event, condition, lifecycle state, boot session,
sequence, and observed age. Each Heltec recorded exactly +1 sent, +1 received,
+1 flood TX, and +1 flood RX per cycle. Both Heltecs and the SenseCAP recorded
zero new core/receive errors; endpoint queues ended empty. The SenseCAP stayed
repeat-on. Temporary channel cleanup passed 4/4 endpoint checks across the two
cycles and no lease journal remained.

## What this proves

- The normative `OGA0` and responder-produced correlated `OGK0` frames each fit
  and survive the current MeshCore text adapter byte-for-byte.
- The OpenTrail host ingress/responder path can sit between the two physical
  radio legs and preserve all ACK correlation fields in both endpoint roles.
- The SenseCAP observed and retransmitted two flood frames per cycle without
  errors or configuration change.

## What remains unproven

- The host supplied the authenticated/authorized context; MeshCore channel
  membership was not bound to the application producer/consumer identity.
- The Heltecs still run MeshCore Companion firmware, not a direct OpenTrail
  SX1262 target or on-device alert/ACK application.
- Close-bench reception may be direct. Repeater counter deltas show forwarding
  activity but do not prove these cycles required the repeater; the separate
  OT-009 repeat-off negative control supplies that logical-route evidence.
- Loss, corruption, duplicate, delay, reordering, restart/rebind, revoke,
  outbox completion, and field range remain separate gates.
