# OT-060 Android foreground-screen and physical-install evidence

Date: 2026-08-16

## Accepted scope

OT-060 adds Android's Activity-window `FLAG_KEEP_SCREEN_ON` immediately after
`MainActivity.onCreate()` calls its superclass. The flag applies only while the
Trail Activity is visible. It adds no wake lock, manifest permission,
lock-screen behavior, brightness override, or foreground-service behavior.

## Local validation

- Android-only gate: 56 Gradle tasks executed successfully.
- JVM tests: 135 across 13 suites, with zero failures, errors, or skips.
- Lint: `No issues found.`
- Debug APK: 9,677,165 bytes.
- SHA-256: `9CE206EEEAE2B13FC5C1092CEF41C226607FD3A9905A5797D4EBE31F3DC7F01C`.
- Manifest inspection: package `io.github.nbjelanovic.otclient`, min SDK 26,
  target SDK 35, optional BLE, and the previously accepted permission surface.
  No `WAKE_LOCK`, location, internet, or storage permission is present.

## Physical Android acceptance

One owner-authorized physical Android 16 / API 36 handset received the exact
APK above through ADB. No emulator or simulator path was used. The prior temporary Trail test
copy was absent before the accepted install completed.

The handset's original USB stay-awake value was restored before the screen test.
Its normal screen timeout was 30 seconds. With Trail visible and untouched for
40 seconds:

- the exact Trail window retained the `KEEP_SCREEN_ON` flag bit;
- Android remained awake and interactive;
- the built-in display remained on at brightness 0.3529412, while the device's
  reported dim brightness was 0.050980393;
- sending Trail to Home removed it from focus, and reopening it succeeded.

The same exact APK reached the explicit Local test surface. The UI remained
visibly fake/deterministic, displayed no Bluetooth permission prompt, and did
not start `TrailConnectedDeviceService`.

## Boundaries

This proves one debug APK install/launch and foreground screen-retention behavior
on one physical Android handset. It does not prove release signing, store
distribution, battery life, heat, OLED burn-in endurance, manual-lock behavior,
TalkBack, notification lifecycle, Bluetooth scanning/pairing, application
authorization, a Ready session, LoRa/GNSS behavior, or OpenTrail firmware on a
physical target. No phone serial, build fingerprint, account, notification,
coordinate, MAC address, or other private identifier is retained here.

The V1 measure remains 30% because canonical V1 requires phone-independent
self-contained clients. The next functional gate is recovery-first flashing and
runtime acceptance on one explicitly selected OpenTrail hardware target.
