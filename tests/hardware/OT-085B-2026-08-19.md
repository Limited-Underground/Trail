## Harness correction and validation

An initial invocation stopped before BLE activity because the generated test
package registered the default runner instead of the bounded acceptance
instrumentation. The application now explicitly registers the custom test-only
runner, and the standard Android gate compiles the instrumentation APK.

The first real BLE attempt accepted the public read and timed target-side
disconnect, and the owner observed the complete OLED lifecycle, but its overall
result was DENY because the harness required equality with the originally
selected `BluetoothDevice`. That postcondition was rejected: the target uses a
privacy-aware resolvable private address, while Android's device object wraps a
hardware address, so equality cannot establish persistent physical identity
across advertising restart.

The final harness instead requires exactly one service-filtered advertiser
before and after the passive link. It retains all prior exact GATT, phase,
property, value, monotonic timing, callback-status, and no-identity checks. It
contains no phone disconnect call, no automatic reconnect, and no detailed
failure output. The installed test package registered exactly
`io.github.nbjelanovic.otclient.PublicLinkProbeInstrumentation`. The final
validated artifacts were:

- 12,253,086-byte debug APK, SHA-256
  `696368012B9F55AD7294B69265D04F7874A553CFB7899775D096BA0E03F96EA4`;
- 16,985-byte instrumentation APK, SHA-256
  `897DC7EFD8E235AA1A5C8B5C4BBD03C6F3B6C71F0CA8EE7CB844C68ADC3CA060`.

The Android gate passes 139 JVM tests across fifteen suites with zero failures,
errors, or skips, warning-as-error lint, debug assembly, and instrumentation
assembly. The Heltec target admission suite passes all twelve groups.

## Boundary

This accepts one fixed public read, the firmware-driven timeout and disconnect,
the owner-observed connected-to-advertising display lifecycle, and return of one
compatible service advertiser. It does not claim a stable BLE identity.

`BLE CONNECTED` means only that one BLE transport link existed. This result
does not prove pairing, encryption, authenticated bonding, ownership, trusted
phone state, protected Protocol Info/Command/Stream access, provisioning,
persistence, Ready, messaging, LoRa, GNSS, complete recovery, power endurance,
operational release, field operation, regulatory acceptance, or supported
hardware. Decision 0028 remains in force.
