# OT-019O Heltec maintenance-failure recovery evidence — 2026-08-13

Status: passed for manual USB/runtime recovery; low-level hardware profiling
remains unresolved

## Scope

This record covers one assembled Heltec V4 OLED bench client, inventory label
`OT-DEV-002`, after a single supervised read-only attempt to query its ESP32 ROM
identity. It tests whether the installed MeshCore runtime returns after that
attempt fails. It does not establish an automatic recovery path, exact board
revision, supported hardware profile, or permission to write firmware.

Local port assignments, serial/hardware identifiers, pairing material, raw
device responses, public keys, and coordinates are deliberately excluded.

## Prestate

Normal MeshCore USB inspection succeeded before the attempt and reported:

- Heltec V4 OLED, MeshCore `v1.16.0-07a3ca9`, companion role;
- repeat disabled;
- 910.525 MHz, 62.5 kHz bandwidth, SF7, CR5, 10 dBm configured transmit
  power, and 22 dBm reported maximum;
- 4.069 V battery, zero runtime errors, and an empty queue.

The other Heltec companion and the SenseCAP repeater were not selected for the
maintenance attempt.

## Bounded attempt

The one allowed command used `esptool 5.3.1` with two connection tries,
`--no-stub`, and the read-only `chip-id` operation. Default/hard-reset line
handling was requested only to try to enter and leave the ROM session.

The host failed while configuring the serial endpoint, before an ESP32 ROM
connection was established. No chip identity was returned; no stub was loaded;
and no flash read, erase, write, eFuse change, or firmware action occurred.
The attempt was not repeated.

## Recovery observations

Immediately afterward, Windows still enumerated three USB candidates, but the
selected Heltec no longer answered the bounded MeshCore runtime query. A normal
runtime-only recheck five seconds later had the same result. It was not reset
or probed again.

The affected candidate was subsequently absent while the other Heltec and the
SenseCAP remained healthy. After USB reconnection/re-enumeration, the complete
privacy-safe inspection again reported:

`3 USB candidates found · 3 runtime-identified · 0 ready to flash`

A normal MeshCore post-recovery read of `OT-DEV-002` then reported the same
model, firmware, companion role, repeat setting, and radio configuration as the
prestate. Battery remained 4.069 V; uptime was 133 seconds; runtime errors,
queue length, packet counts, airtime, and receive errors were all zero.

## Result and limits

The device returned to a healthy installed MeshCore runtime after manual USB
reconnection/re-enumeration, with no observed configuration loss. This closes
only the bounded recovery observation for this unit on this laptop.

The automatic ESP32 ROM-entry path failed and remains unsupported. Exact MCU,
PSRAM, flash, crystal, security-fuse, received-revision, RF-variant, bootloader,
and product-role evidence remain unresolved. A later maintenance design must
retain the one-attempt rule, stop immediately after failure, and require normal
runtime recovery before another session is considered.
