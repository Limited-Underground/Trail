# OT-101 host-only compact status footer prototype

- Date: 2026-08-21
- Status: `partial`
- Host implementation: `tests/host_support/compact_status_footer.hpp` and `tests/host_support/compact_status_footer.cpp`
- Focused test: `tests/host/compact_status_footer_tests.cpp`
- Full host gate: `tools/Test-Host.ps1`, exit zero, session 4000

OT-101 now has a target-neutral host-only prototype and behavioral contract for
the owner-finalized compact footer. It formats battery, GPS satellite count,
and BLE state as `BAT:100% GPS:12 BLE:C` within one exact 128-column by 8-row
one-bit page. A separate five-column field renders one latest-direction glyph:
`↑` for an injected accepted TX event, `↓` for an injected accepted RX event,
or blank while idle, unsupported, future-dated, expired, or cleared.

Battery accepts only valid values from 0 through 100 and GPS accepts only valid
values from 0 through 99. Each observation has its own nonzero freshness
window. Unavailable, invalid, out-of-range, future, and expired observations
fail closed to `BAT:--%` or `GPS:--`. BLE uses the bounded legend `-`
unavailable, `S` starting, `A` advertising, `C` connected, `R` retrying,
and `E` error; unknown values render as unavailable.

The activity owner is a host seam, not a transport binding. When configured as
supported with a nonzero visibility interval, it admits only TX or RX, keeps
the latest accepted direction, permits equal-time replacement, rejects
regressive timestamps, hides future observations, and blanks exactly at
expiry. Unsupported transport, zero lifetime, invalid direction, and explicit
clear remain blank. A future target adapter may call this seam only after real
LoRa transport definitively accepts an event; no such adapter exists or is
accepted here.

Twelve focused C++17 warnings-as-errors scenario groups pass. They cover exact
digits and punctuation, percent and dash glyphs, both arrow glyphs, field
widths, the exact 128-column golden page, geometry and gaps, invalid/unknown
fail-closed behavior, battery/GPS validity and freshness boundaries, BLE codes,
latest/equal/regressive event ordering, monotonic expiry, unsupported
transport, clear, and unsigned-64 boundary behavior. The authoritative full
host gate also passes with exit zero in session 4000, including both
publication-safety gates, the 59-group warning-free Windows loader tail,
33/0 simulator core, 23/0 Windows bridge, 15 private bridge, 10/0 portable
protocol, and 13/13 UI groups.

The prototype is deliberately stored under `tests/host_support`, not the
firmware tree. It is not linked into or built for an ESP-IDF target and has no
target renderer or OLED driver, battery source, GNSS-satellite source, BLE
runtime source, radio event source, or accepted traffic binding. No device was
accessed or flashed. This evidence proves no firmware or target build, physical
display, sensor telemetry, BLE/radio traffic, support, compatibility,
regulatory acceptance, or V1 score change.
