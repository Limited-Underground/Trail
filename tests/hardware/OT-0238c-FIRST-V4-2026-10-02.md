## What the source review establishes

`candidate_boot_verified` checks candidate/protected pins, factory selection,
the guarded native reset path and closed ROM ownership. It does not check the
application's HELLO or BOOTSTATUS response. The startup display renders its logo
before input, durable storage and runtime initialization; either normal idle or
a later initialization stop can retain that logo. The logo alone distinguishes
neither case.

The first enrollment event is retained only after startup/HELLO and the initial
identity exchange. Zero checkpoint events therefore means zero retained human
checkpoints, not zero commands. HELLO can wait for the full remaining ceiling;
that is a source-supported possibility, not a proven cause in this attempt.

`Controller.run()` returns its own first failure. `_BoundOperator.run()` checks
the clock after that return but before forwarding the result, and custody checks
its budget before consuming the returned result. Either later check can replace
an earlier controller failure. The surviving deadline fault cannot be treated
as proof that expiry was the first physical failure.

Existing candidate BOOTSTATUS distinguishes runtime-ready 0 from initialization
stop stages 1-9. No extra diagnostic command was issued during restoration or
after expiry. A future diagnostic read needs fresh bounded physical authority.
