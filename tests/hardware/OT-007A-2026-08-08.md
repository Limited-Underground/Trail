# OT-007A Two-Node Transport Characterization

Date: 2026-08-08

Status: complete for bounded bench characterization; RSSI and fine-grained airtime remain firmware measurement limitations

## Setup

- `OT-DEV-001`: Heltec V4 OLED, MeshCore USB Companion `v1.16.0-07a3ca9`, `COM6`
- `OT-DEV-002`: Heltec V4 OLED, MeshCore USB Companion `v1.16.0-07a3ca9`, `COM11`
- Both configured for the user-selected USA/Canada preset: 910.525 MHz, BW 62.5 kHz, SF7, CR5, 10 dBm, repeat disabled
- Both LoRa antennas confirmed attached by the user
- Both connected to the same development laptop over independent USB serial ports
- Initial baseline on both: 0 errors, empty queues, 0 packets sent/received, 0 receive errors, and 0 reported transmit/receive airtime

## Bounded investigation

Nine short, non-sensitive channel-0 test markers were transmitted in total: five from `OT-DEV-001` to `OT-DEV-002` and four in the reverse direction.

1. Two initial two-direction runs established packet reception, but the harness reported false application timeouts.
2. A read-only comparison proved channel 0 names and secret bytes matched internally, each channel hash had only one candidate, both nodes had distinct identities, and neither had a default flood scope configured.
3. `OT-DEV-002` was about 816 days behind `OT-DEV-001`; both clocks were synchronized. A two-direction retry with the old assertion still reported false timeouts, proving clock skew was not the root cause.
4. A one-direction raw-RX diagnostic proved the received frame was `GRP_TXT` over `FLOOD`, its channel hash matched, its MAC validated, it decrypted, the firmware emitted `MESSAGES_WAITING`, and `get_msg` returned a channel message.
5. The harness was corrected to match its unique marker within MeshCore's returned display text. The final one-message-per-direction run passed.

No advert, repeat, location, identity change, key export, factory reset, or radio-configuration command was issued. The only device-state change was synchronizing both clocks to the current UTC epoch.

## Root cause of the earlier false negatives

The radios and firmware queue were working. The test harness required the entire received display text to equal its random marker. MeshCore channel messages include sender display text around the application message, so the correct assertion is that the returned text contains the unique marker. After that narrow correction, both directions passed immediately.

The firmware source also shows that its packet-received counter increments before channel lookup, MAC validation, and decryption. Packet counters alone were therefore insufficient evidence; the raw-RX and queue checks were necessary to establish authenticated application delivery.

## Private numbered sample

A shared empty channel slot was configured on both devices with a temporary in-memory-only secret. Five numbered messages were sent in each direction, after which the channel was erased and verified empty on both companions.

| Direction | Delivered | Lost | Duplicates | Latency min/median/max | SNR min/median/max |
| --- | ---: | ---: | ---: | ---: | ---: |
| `OT-DEV-001` to `OT-DEV-002` | 5/5 | 0 | 0 | 233.3 / 234.8 / 247.2 ms | 11.5 / 12.0 / 12.25 dB |
| `OT-DEV-002` to `OT-DEV-001` | 5/5 | 0 | 0 | 236.0 / 237.6 / 241.8 ms | 11.25 / 12.0 / 12.25 dB |

Each device recorded exactly +5 packets sent, +5 received, +5 flood TX, and +5 flood RX. Both recorded 0 new core errors, 0 receive errors, and an empty final queue. The coarse firmware counters increased by 1 second for TX airtime and 1 second for RX airtime on each device.

After cleanup, final cumulative counters for the complete investigation were 10 sent/9 received on `OT-DEV-001` and 9 sent/10 received on `OT-DEV-002`, matching the intentionally asymmetric one-way raw diagnostic. Both clocks remained synchronized within one second, both queues were empty, and both error counts remained zero.

## Remaining limitations

- The reported RSSI remained `0`, which is invalid/unusable. Raw-RX logging also reported `0`.
- Firmware airtime counters have whole-second resolution. They changed by 0 or 1 second during these very short runs and are not suitable for per-packet airtime measurement.
- The test used MeshCore's `Public` channel. Payload markers contained no user data, but MeshCore channel text includes the device display name and may be visible to nearby compatible receivers; the transmissions were not truly anonymous.
- The ten-message numbered sample used a temporary private channel and does not establish long-range, obstructed-path, mobility, congestion, reboot, or multi-node performance.

## Next bounded step

Use these measurements to define the initial radio transport abstraction and experimental packet budget. Keep regulatory review and later range/mobility testing as separate gates; do not infer field performance from this close-range USB-powered bench result.
