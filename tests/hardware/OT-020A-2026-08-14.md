# OT-020A Host-Only Wio GNSS Lifecycle/Recovery Coordinator Contract

Date: 2026-08-14

Status: accepted host-only prerequisite; no live device or GNSS evidence

## Purpose

Establish a fail-closed host-side coordinator contract before any supervised
Wio GNSS activation is attempted. The contract owns temporary GPS enablement,
verified restoration to the original off state, recovery authority, and a
non-transmission guard. It is not a real Wio adapter and does not validate a
fix, no-fix, stale, loss, or reacquisition sequence.

## Evidence boundary

The accepted implementation uses synthetic injected adapters only. It has no
serial, USB, PnP, BLE, or MeshCore dependency and is not wired to the connected
Wio. No live adapter or device I/O, setting change, transmission, coordinate,
identity, channel value, BLE datum, reset, DFU action, or flash occurred.

The 2026-08-13 device observation remains unchanged: the owner-reported Wio
Tracker L1 Pro had already been flashed and configured before inspection, so
its shipping/pre-write state was not preserved or verified. That read-only pass
found GNSS detected, inactive, and without GPS telemetry.

## Coordinator contract

A normal lifecycle may proceed only after all of these conditions hold:

- one exclusive lease is acquired and no recovery journal already exists;
- exactly one injected adapter matches public USB family `2886:1667`, public
  model `Seeed Wio Tracker L1`, companion role, supported firmware
  `v1.17.0-727fc05`, and an opaque exact-device binding token;
- location advert policy is `none`, telemetry permission is `deny`, and GPS is
  read back as off; and
- transmit counters are structurally valid with zero pending work.

Before the coordinator may request GPS on, it creates a durable no-overwrite
`restore_required` journal bound to that exact target. An enable acknowledgement
is never trusted by itself: GPS state is read back. A verified on state advances
the journal to `enabled_verified` through expected-record comparison. The only
GNSS observation exposed is whether a telemetry field is present; its content
is never requested or returned.

Every post-journal path requests GPS off exactly once and verifies the off state
by readback. It then revalidates the exact target binding before deleting the
journal through expected-record comparison. Restoration uncertainty, target
change, or journal conflict retains recovery authority.

After verified restoration, two counter snapshots must be identical to each
other and to the baseline, retain the same session-scoped continuity token, and
keep pending work at zero. Counter reset, continuity-token change, newly pending
work, any packet/airtime/flood/direct delta, or an unsettled second read
invalidates the non-transmission guard. At this lifecycle layer the token is an
equality marker, not a device boot identity; independently trustworthy
transport-generation and monotonic-uptime evidence remain adapter obligations.

An existing journal blocks normal mode. The separate recovery-only entry point
matches the exact journal binding, can only verify or request GPS off, rechecks
the target after restoration, and removes the journal only after verified
success. It never exposes a GPS-enable operation and is idempotent when GPS is
already off.

### 2026-08-14 authority terminology clarification

The original lifecycle implementation retains the internal field name
`boot_token`. Its accepted synthetic result proves only that one opaque token
remains equal across the lifecycle's baseline and restored counter snapshots.
It does not prove that the token came from a device, identify a device boot, or
independently rule out reboot. Public evidence therefore calls it a session-
scoped continuity token. This terminology correction does not add to or rewrite
the original 15-group result.

The expected-record file operations rely on the injected exclusive lease for
serialization; they are not an operating-system atomic compare-and-swap. A
future live adapter must supply an authoritative lease, trustworthy opaque HMAC
target binding, a session-scoped continuity token, independently trustworthy
transport-generation and monotonic-uptime observations, and a real quiet
interval around the two settled counter snapshots. Until that authority exists
and the live command/readback and autonomous-advert behavior are independently
accepted, this coordinator cannot authorize a hardware run.

## Interpretation and remaining gates

OT-020 remains `partial`, and the unit remains `experimented` for
USB/runtime/configuration evidence only. This host-only prerequisite does not
advance Wio compatibility, validation, or support. The entire live GNSS phase
remains open, including supervised enablement and final off readback, first fix,
accuracy, cadence, stale/loss/reacquisition behavior, and power cost without
retaining coordinates. Exact label/SKU/revision, over-air interoperability,
antenna/RF/regulatory, BLE, DFU/firmware recovery, power/endurance, and clean-
machine evidence also remain open.

This result does not change the evidence-weighted V1 percentage.
