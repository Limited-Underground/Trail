# OT-020B Host-Only Wio GNSS Windows Authority Boundary

Date: 2026-08-14

Evidence class: deterministic Windows host authority

Result: accepted host-only prerequisite; no live device or GNSS evidence

## Purpose

Supply the Windows-side authority that the OT-020A lifecycle/recovery
coordinator requires before a future supervised Wio GNSS adapter may be
considered. This boundary owns a private binding key, opaque continuity tokens,
exclusive per-target host ownership, and settled counter observations. It is
deliberately below discovery and command transport.

## Evidence boundary

The authority module and its focused tests contain no serial, USB, PnP, BLE, or
MeshCore dependency, no device-access path, and no live or mutable device-command
surface. All adapter-facing values are synthetic, already reduced observations.
No port was enumerated or opened, no hardware was queried, no setting changed,
and no radio, GNSS, BLE, DFU, reset, or flash action occurred.

OT-020B does write bounded local authority state during its native Windows
tests: a DPAPI CurrentUser-protected key file and named-mutex ownership. Those
host operations do not communicate with a device.

## Accepted authority contract

### Private key and bindings

- One exact 32-byte HMAC key is protected through Windows DPAPI CurrentUser.
  Protected-file reads are bounded, creation is no-overwrite, and concurrent
  first writers converge on the retained key rather than replacing it.
- An exact target token is derived from exactly one bounded private source with
  a domain-separated HMAC. The source is not normalized, logged, serialized,
  returned, or included in failures.
- A second domain derives a session-scoped continuity token from the target
  token and a fresh session nonce. This token is not a device boot identity.
  Future reboot continuity instead depends on the adapter correctly advancing
  transport generation and supplying trustworthy monotonic uptime.

### Exclusive per-target lease

- A domain-separated digest of the target token names one nonblocking Windows
  mutex. Same-process and cross-process attempts for that target cannot both
  acquire authority.
- Ordinary busy state returns without blocking. Abandoned ownership, a race
  after native acquisition, wait failure, and release or handle-close
  uncertainty fail closed.
- Uncertain cleanup poisons that target for the rest of the process instead of
  allowing a second owner. Native process-death recovery is covered.

### Settled counter authority

- The injected observation contains only transport generation, monotonic
  uptime, pending work, packet count, airtime, flood count, and direct count.
- Each settled read takes two observations around a requested five-second quiet
  interval. Transport generation must stay unchanged, uptime must advance
  plausibly, pending work must remain zero, and every traffic counter must be
  identical across the interval.
- Continuity between accepted windows is bounded. A previous-window gap of
  exactly 180 seconds passes; 180.001 seconds fails closed. Longer observation
  work must re-establish authority instead of silently extending it.
- Invalid data, counter rollback, generation change, implausible uptime,
  pending work, in-window traffic, wait/clock/read failure, or timing ambiguity
  latches the counter authority closed. Raw injected exceptions do not survive
  in fixed errors or formatted traceback output.

### OT-020A integration

The integration uses only synthetic adapters. It proves that the authority can
supply OT-020A with a target token, session-scoped continuity token, exclusive
lease, and reduced counters while OT-020A retains responsibility for journal-
before-enable ordering, acknowledgement/readback, GPS-off restoration, recovery-
only handling, post-restore binding, and final baseline comparison. OT-020B
itself exposes none of those device commands.

The authority groups cover fixed HMAC vectors and domain separation; bounded,

That aggregate host gate separately ran its pre-existing privacy-safe read-only

## Interpretation and remaining gates

OT-020 remains `partial`, and the Wio remains `experimented` for its earlier
USB/runtime/configuration evidence only. OT-020B does not identify the exact
received SKU/revision, authorize radio operation, validate an antenna, or prove
live GNSS, compatibility, support, recovery, or power behavior.

A future adapter must still provide stable private-source selection,
authoritative transport-generation semantics, trustworthy monotonic uptime,
the real command/readback translation, autonomous-advert behavior, and a
supervised live safety review. Current native evidence is within the same
Windows session; it does not establish cross-session mutex exclusivity,
abrupt-power-loss file durability, or live Wio behavior.

The missing shipping/pre-write state and the entire live GNSS phase remain
open. This result does not change the evidence-weighted V1 percentage.
