# OT-020 Wio Tracker L1 Pro First USB and Runtime Pass

Date: 2026-08-13

Evidence class: bounded connected-bench experiment

Result: partial pass for USB/runtime/configuration evidence only

Final classification: `experimented`; not `validated`, compatible, or
supported

## Purpose

Identify the newly connected Wio Tracker candidate and collect a privacy-safe,
read-only MeshCore runtime snapshot without transmitting, changing settings,
entering recovery, or retaining device identity, channel secrets, or location.

## Acquisition and preservation boundary

The owner identifies the unit as a Wio Tracker L1 Pro and reports that it had
already been flashed as a MeshCore USB Companion and configured for a USA
frequency plan before this inspection began. The shipping/pre-write firmware,
role, configuration, exact flasher selection, and erase state therefore were
not preserved or independently verified.

Windows exposed the public USB model `Seeed Wio Tracker L1` on USB family
`2886:1667`. That runtime descriptor is consistent with the reported product
family, but it does not establish the exact Pro SKU, retail variant, hardware
revision, RF front end, antenna, or regulatory authorization. The cable was
data-capable; its make/model and the exact Windows host build were not recorded.
No browser or flasher was used during this pass, and their earlier versions
were not available as evidence.

Local serial-port assignments were used only inside the live inspection and
are deliberately omitted because they are transient. No USB serial number,
PnP instance path, MeshCore identity, public key, PIN, MAC/BLE address, channel
value, or coordinate was printed or retained in this public record.

## Method

1. A Windows Ports/PnP query reduced the current device to COM-independent
   public model, USB family, interface description, and healthy enumeration
   status.
2. A fixed read-only MeshCLI path requested the allowlisted version,
   configuration, core, radio, and packet statistics needed below. It exposed
   no reset, reboot, setting, transmit, channel-write, erase, or flash action.
3. The same reduced snapshot was repeated three more times. Only public model,
   firmware/profile values, increasing uptime, battery voltage, and aggregate
   error/traffic counters were retained.
4. A non-transmitting comparison with the one connected Heltec companion
   reduced private channel/default-scope/identity data in memory to boolean
   match/distinct results and a coarse clock delta. Secret and identity values
   were never emitted.
5. Mounted volumes were checked without requesting DFU. No `TRACKER L1` volume
   was present in the normal-runtime snapshot.

The installed MeshCLI package version was not re-recorded for this pass. That
omission remains part of the evidence boundary; the firmware version below is
the connected device's reported value.

## Non-transmitting Heltec comparison

The connected Wio and remaining Heltec companion produced these reduced
results without sending a radio packet:

- channel 0 name, hash, and secret matched in memory; none of those values was
  output or saved;
- neither device had a default flood scope configured, so their default-scope
  state matched;
- device identities were distinct, with neither identity emitted; and
- reported clocks were within one second.

This proves only a privacy-safe configuration comparison. It is not an advert,
contact, message-delivery, over-air interoperability, latency, loss, duplicate,
RSSI/SNR, range, or cleanup result.

## Actions deliberately not performed

- no transmission or temporary channel/contact creation
- no BLE discovery, pairing, or connection
- no DFU/recovery entry or exit
- no reset, reboot, line toggle, erase, flash, or setting change
- no coordinate request or capture
- no clean-machine or packaged Windows-utility validation

## Loader follow-up on 2026-08-14

The current-tree C# and Python loaders subsequently accepted this Wio family.
The warning-free C# suite passed 59 groups. Three consecutive built-in
production refreshes returned the expected one-Heltec, one-SenseCAP, one-Wio
roster, all three runtime-identified and zero ready to flash, without emitting
local ports.

The new failure-to-recovery group found that a collapsed error peer could keep
stale assertive text after the device roster recovered. The corrected hidden
peer clears text, Automation ID, and help and uses live setting Off; only an
actual current visible failure exposes assertive error content. The recovered
automation tree contains no stale error.

The replacement 464-file source-free package containing those corrections then
passed independent manifest/hash/extraction/launch verification and three
native external UI Automation selection/Refresh/live-event/heading cycles. The
external verifier required the exact public roster `Heltec V4 OLED`, `SenseCAP
Solar`, and `Wio Tracker L1`; every cycle returned zero ready to flash. This is
loader/package recognition evidence only, not injected packaged failure,
clean-machine, or hardware-compatibility evidence.

## Interpretation and remaining gates

OT-020 advances from `planned` to `partial`, and the unit is classified only as
`experimented` for USB/runtime/configuration evidence. The following remain
open:

- exact exterior label, SKU, hardware revision, RF variant, and supplied or
  installed antenna
- shipping/pre-write firmware and configuration, which cannot be recovered
  from this pass
- intentional over-air Heltec interoperability with packet, loss, duplicate,
  latency, signal, airtime, and cleanup evidence
- GNSS activation, first fix, accuracy, stale/loss/recovery behavior, update
  cadence, and power cost without retaining coordinates
- antenna/RF characterization, FCC grant and instruction review, and US
  regulatory authorization for the exact configuration
- charging, battery endurance, solar behavior, environmental behavior, and
  power-state transitions
- BLE operation and privacy behavior
- non-destructive DFU entry/exit, rollback/recovery, and failure handling
- repeatability on another cable/host and clean-machine operation

No OpenTrail supported-hardware, compatibility, validated-hardware, field-use,
or production-readiness claim follows from this experiment.
